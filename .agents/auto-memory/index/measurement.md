# measurement — probes, ratios, controls, and what a number does NOT mean

Full hooks for this area. The routing keys live in `.agents/auto-memory/MEMORY.md`; the memories themselves in `.agents/auto-memory/<slug>.md`.

- [musl is not why alpine browsers are slower](project_alpine_browser_perf_vs_glibc.md) — FF and WK at parity or FASTER than official glibc; only chromium regressed (build config); perf-firefox's THREE arms split env from build (its ubuntu arm ships PW's binary, not ours) — our FF's real deltas are screenshot/launch/layout, while eval_rtt is our image
- [The perf-probe ratio is runner-CPU-dependent](project_perf_probe_ratio_is_cpu_dependent.md) — each run is internally runner-divided but two runs still cannot be differenced across CPU models; `libm_fmod` is the free fingerprint (5.35 EPYC 7763 / 6.3 EPYC 9V74 / 7.65 Xeon 8370C at CV 0.5%) — pair arm-to-control by CPU and confirm on it before reading anything; fleet mix measured over 19 runs — 7763 50%, 9V74 25%, three Xeons the rest — so a given model is a ~1-in-4 lottery, reachable by a background re-dispatch loop that reads the CPU per run
- [PNG encoder exposure by browser](project_png_encoder_exposure_by_browser.md) — only FF paid it; wk and chr match official byte-for-byte on the canvas control; libpng-vs-zlib now SEPARATED — zlib exonerated, libpng carries it
- [Probe font mismatch confounds layout](project_probe_font_mismatch_confounds_layout.md) — the fixture sets no font-family; ours resolves FreeSans, official's collapses serif/sans-serif/unknown onto one CJK face (wqy-zenhei); real for the painting rows but it does NOT explain layout (text/box-only ratio is ~1.0 in BOTH images, so shaping is not re-paid per reflow)
- [runtime-probe rows are batches, not single ops](project_runtime_probe_rows_are_batches.md) — `screenshot` is 10 shots per row while the encode probe reports per shot; differencing the two invented a 24 ms "capture" phantom that no profile could find
- [Two of three browsers are AT parity, chromium is the residual](project_three_model_parity_state.md) — 3-model x 2-draw campaign 2026-09-09: firefox and webkit <= 1.00-1.05 on every row on 7763/9V74/8573C; chromium `launch` 1.40-1.45 (CPU-independent, the DSO closure), `layout` 1.62 on 7763 but 1.24-1.28 elsewhere (our arm gains MORE from faster silicon, so 1.62 is a worst case), `screenshot` 1.22 on the 9V74 only and that is frame spill, not speed
- [FF probe: three pinned rows + 1 ms timer grain](project_ff_probe_pinned_rows_and_timer_grain.md) — locator_click AND click_force (100 x 16.667 ms = one 60Hz frame, firefox only) AND int_math (imul latency, 37-39 ms across three JS engines) cannot move; every firefox in-page kernel is measured at 1 ms grain so js_alloc has +-5% resolution, fixed by `privacy.reduceTimerPrecision:false` (verified: 1 ms -> 0.02 ms); and at n=10 TEN of thirteen rows are statistically TIED (context_page was 25/25 'clean' at n=5, 69/100 at n=10) so most of the parity goal is not decidable with these kernels
- [Runtime perf probe](project_runtime_perf_probe.md) — measures execution speed of shipped browsers; one job per browser (runner CPUs vary per job); locator_click is frame-bound, click_force discriminates
- [Source-tag probe pattern: uniform *_SOURCE_TAG + scoped dispatch guard + same-machine assert](project_source_tag_probe_pattern.md) — probe an unmerged branch's artifact without merging or cross-CPU noise (PRs #160-162); also: an override-built "proof image" doesn't prove the default (unpinned) build path ships the fix
- [The libm_fmod KERNEL was vacuous too](project_libm_fmod_kernel_was_vacuous_too.md) — shipped with a 2^32 divisor and reached libc ZERO times under WebKit (counted), so every libm_fmod verdict including firefox's 0.64 win is void; the "power-of-two theory is wrong" note was V8-only and did not transfer to JSC; `pw_run.sh` OVERWRITES an inherited LD_PRELOAD
- [screenshot row is frame-quantized on chromium+webkit](project_screenshot_row_is_frame_quantized.md) — per-shot cost lands on multiples of 16.667 ms, so the ratio steps between small integer quotients; chromium's 1.00 on a 7763 is both arms inside one 3-frame budget (ours spills to 3.31 and misses entirely on a 9V74), and webkit's 0.66 is 2 frames vs 3, not a continuous win; only firefox measures speed there
- [libm_fmod is musl's fmod — and both C microbenches were VACUOUS](project_fmod_microbench_is_vacuous.md) — gcc 15 inlines `fmod` on a power-of-two divisor so the timing loop never called libc while `nm -D` still showed the import; `-fno-builtin-fmod` + a call-count gate give glibc 54 ms vs musl 164 ms, and a bit-exact branchless rewrite hits 64.5 ms (issue #126)
- [A CI build's duration is not evidence of what rebuilt](project_gha_build_duration_not_evidence.md) — a 21-second consumer build after a producer retag looked like a no-op but was a correct cache hit; verify with the artifact's own probe output/digest/revision label, never duration
- [The probe's ubuntu arm is two node majors behind](project_probe_node_version_split.md) — v22.23.2 vs v24.18.1 on alpine+official, splitting eval_rtt into a fixable ubuntu pin and an unexplained alpine residual
- [Bench baseline is load-bearing](feedback_bench_baseline_load_bearing.md) — never drop `baseline` from the PW bench matrix; it's the comparison reference for every Δ column
- [musl's mallocng mmaps the DRIVER, not the browser](project_musl_mallocng_mmaps_the_driver.md) — 44,491 munmaps against glibc's 78, 20,866 of them at exactly 69,632 B with only 78 `clone` calls (so not thread stacks); the allocations are node's, and `ENV LD_PRELOAD=mimalloc` + a MANDATORY chromium shim (unshielded chromium will not start) takes wk click_force 1.15->1.00 and eval_rtt 1.10->0.99, PR #136
- [The probe's per-metric noise floor](project_perf_probe_resolution_floor.md) — a null pair (same image, same CPU model, two runs=5) says goto_cold cannot resolve better than 0.12 and click_force 0.07, while goto_warm/layout/eval_rtt/int_math resolve to 0.01 or better; check any delta against its row's floor before quoting it
